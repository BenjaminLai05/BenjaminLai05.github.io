System Design

  • Route Architecture: Five modular Express routers — index.js (public routes), users.js (member actions), managers.js (org management), admins.js (platform oversight), and organisations.js (org data retrieval).
  • Session-Based Auth: express-session with secure, HTTP-only cookies. Three middleware guards (checkUserSession, checkManagerSession, checkAdminSession) protecting routes based on permission level.
  • Database Schema: Seven relational tables — users, organisations, events, updates, plus three join tables (user_organisation, user_event, manager_organisation) enforcing referential integrity via Foreign Key constraints.
  • File Uploads: Multer middleware handles profile picture and organisation image uploads, storing binary data as MEDIUMBLOB in MySQL.
  • Rate Limiting: express-slow-down throttles requests after 100 hits per 15-minute window, adding 200ms delays to mitigate abuse.

Technical Trade-offs

  • MySQL over NoSQL: The highly relational nature of Users ↔ Organisations ↔ Events required strict FK constraints and join-table integrity that document stores cannot enforce natively.
  • Server-Side Rendering over SPA: Static HTML served from Express with AJAX calls for dynamic data. Avoided React/Vue overhead for a CRUD-heavy app where server-rendered pages kept the architecture simpler.
  • BLOB Storage over File System: Profile images stored directly in MySQL as MEDIUMBLOB. Trade-off: simpler deployment (no CDN), but increased database size and query overhead for image retrieval.
  • Session Cookies over JWT: Used express-session for server-side state. Trade-off: requires session storage server-side, but provides immediate revocation and simpler CSRF protection.

NBA Elo Predictor

CLI Navigation & Features

The system is packaged into a robust Python CLI application. Navigation is hierarchical and menu-driven, separating heavy scraping pipelines from daily prediction tasks.

1. Run Historical Backtest

  • Evaluates model accuracy over an entire past season.
  • Supports two prediction profiles: Accuracy Mode (maximizes raw correct picks) and Calibrated Mode (better probability mapping for betting ROI).

2. Live Predict (Daily Sync)

  • Fetches today's games, official NBA lineups, and real-time OddsPortal data.
  • Advanced Modeling: Automatically calculates player minute availability.
  • Interactive Options: After generating predictions, users can enter a submenu to "Set Your Own Odds" to calculate dynamic implied probabilities and find +EV (Expected Value) betting edges against specific bookmakers.

3. Inspect Recent Predictions

  • Deep-dive into specific games from the most recent run.
  • View full side-by-side team rosters, individual player Elo ratings, rotation minutes, and the model's rationale (e.g., Home Court Advantage adjustments).

4. Run Betting Optimisation

  • Executes an algorithmic parameter sweep across historical seasons (2024-2026).
  • Finds the most profitable theoretical betting thresholds by identifying optimal discrepancies between model probabilities and bookmaker odds.

Project Purpose

This CLI application holds a back-testing pipeline that turns Basketball-Reference season data into player-level Elo ratings, rolls those ratings forward game-by-game, and evaluates how well the model's win-probability predictions match real outcomes.

My Role & Contributions

This was a solo end-to-end project. I designed and calibrated the player Elo seeding algorithm (built on PER, WS, and BPM), built the multi-source web scraping pipeline, implemented the live prediction and betting optimisation engine, and packaged the entire system as a distributable standalone application for non-technical users via PyInstaller.

Core Questions Addressed

  • How do individual player ratings evolve through the season?
  • How accurate are our Elo-based game predictions?

Key System Outputs

  • Elo Logs: One row per player per game detailing pre-Elo, minute adjustments, and post-game Elo changes.
  • Game Predictions: Pre-game forecasts matched against true game outcomes to compute rolling system accuracy (currently tracking at ~68.1%).

User Stories

As a Daily NBA Bettor, I want to receive today's win probabilities alongside real-time book odds, so that I can identify +EV (positive expected value) edges before games tip off.
As an Analyst, I want to run a full-season historical backtest, so that I can validate the model's accuracy and compare calibrated vs. accuracy prediction modes.
As a Non-Technical User, I want to run the predictor from a single click without installing Python, so that I can use the tool daily without any development environment setup.

Scope & Constraints

  • Data Source: Dependent on Basketball-Reference and OddsPortal availability; scraping delays are built in to respect rate limits and avoid bot detection.
  • Model Type: Elo-based probabilistic model, not a deep learning approach. Interpretable and computationally lightweight, but bounded by the Elo framework's assumptions.
  • Distribution: CLI-only; no web interface. Windows and Mac builds only via PyInstaller.
  • Season Coverage: Backtesting validated across 2024–2026 NBA seasons.

System Architecture

  • Data Ingestion: Automated scraping layers fetch raw Box Scores and Game Ledgers from Basketball-Reference using rotating user-agents and intelligent request delays.
  • Rating Algorithm: Individual player seeds are built using advanced metrics (PER, WS, BPM). During live backtesting, these ratings dynamically update based on individual performance and point differential weighting.
  • Weighting Mechanism: Before tip-off, win probabilities are constructed by blending team strength based on weighted minutes availability, isolating stars vs. bench rotations.

Technical Decisions

  • Python CLI: Opted for a CLI architecture over a full web-app to focus purely on high-frequency algorithmic accuracy and rapid, daily scraping tasks.
  • CSV Over SQL: Due to the standalone nature of the distributed app and single-user requirement, CSV logs provide sufficient performance without requiring a local database SQL daemon.

Distribution & Portability

To enable non-developer users to run daily predictions, the entire Python scraping and analytical pipeline is bundled into standalone executables:

  • Windows & Mac Builds: Uses build_dist.py and build_dist_mac.py wrappers around PyInstaller to package Python, Pandas, and Playwright browsers seamlessly.
  • Zero-Config Operation: The output is a single folder containing the environment, allowing users to simply run a .command or .bat file without needing pip install or Python in their system PATH.

Quality Assurance & Testing

  • Season-Level Backtesting: The primary validation mechanism — each historical season is replayed game-by-game to verify prediction accuracy against known outcomes, currently achieving ~68.1% accuracy.
  • Calibrated vs. Accuracy Mode: Two configurable prediction profiles are compared to confirm the trade-off between raw correctness and probability calibration for betting ROI purposes.
  • Scraper Fidelity Checks: Box score outputs are spot-checked against known published stats to verify data integrity before Elo updates are applied.
  • Betting Optimisation Sweep: Algorithmic parameter sweeps across 2024–2026 seasons identify which bet thresholds historically yield positive expected value (EV), acting as a validation of the model's probability estimates.

Infrastructure & Environment

  • Local Storage: All data (Elo logs, game predictions, scraped rosters) is persisted as CSV files on disk. No database daemon or server required — the entire state lives in the distribution folder.
  • Playwright Bundled: The Chromium browser used for JS-rendered odds scraping (OddsPortal) is bundled directly into the PyInstaller output, so no separate browser install is needed by end users.
  • Build Pipeline: build_dist.py (Windows) and build_dist_mac.py (Mac) automate the PyInstaller spec generation, dependency resolution, and output folder structuring into a ready-to-distribute package.
  • Cross-Platform: Separate build scripts produce native Windows (.bat) and macOS (.command) launchers for the CLI, requiring zero configuration from the end user.

Project Definition

The MRI Brain Scanner is an advanced medical imaging tool built to assist radiologists in detecting and tracking brain tumours. By leveraging a custom-trained computer vision model, the platform analyzes unstructured medical image data, highlights areas of concern, and calculates precise metrics including changes in tumour count and total tumour area (normalised to total image area).

My Role & Contributions

This was an end-to-end individual project. I was responsible for manually labelling thousands of MRI training images, architecting the YOLO (You Only Look Once) object detection model, building the asynchronous Python (FastAPI) backend, and designing the comprehensive React frontend dashboard you see in the screenshots.

Key Features

  • Automated Tumour Detection: The system automatically draws bounding boxes around detected anomalies with associated confidence percentage scores.
  • Longitudinal Scan Comparison: Allows clinicians to visually and computationally compare two historical scans, calculating a "Confidence Delta" to track tumour growth or shrinkage.
  • Clinical Recommendations Engine: Generates automated preliminary text reports based on the CV model's progression analysis.
  • Interactive Report Editing: Authorized personnel can edit the AI-generated reports and save them back to the patient's file.
  • Responsive UI & Dark Mode: A robust, accessible React interface with a built-in dark mode for extended clinical viewing sessions.

User Stories

As a Radiologist, I want to upload and analyse MRI scans, so that I can quickly detect and localise potential tumour regions with AI-assisted bounding boxes.
As a Clinician, I want to compare two historical scans side-by-side, so that I can track tumour growth or regression over time using objective metrics.
As a Radiologist (Admin), I want to edit and finalise AI-generated reports, so that I can correct model outputs and save accurate clinical records back to the patient file.
As a Physician (Viewer), I want to browse the patient directory and review scan histories, so that I can stay informed on patient status without altering medical records.

Scope & Constraints

  • Dataset: Model trained on a curated, manually labelled dataset of MRI brain scans. Performance is optimised for this specific imaging modality and not generalised across other scan types (e.g., CT, X-ray).
  • Mock Patient Data: Patient records are pre-seeded mock data for demonstration purposes — no real PHI (Protected Health Information) is stored or transmitted.
  • Free-Tier Hosting: Deployed on Railway's free tier; cold starts may take up to one minute as the server allocates memory and loads the ~150MB model weights.
  • Role System: Two hardcoded roles (Radiologist/Admin and Physician/Viewer) simulating a clinical access-control environment.

System Design

  • Frontend Architecture: A Single Page Application (SPA) built with React and Vite. Global state (like the currently selected patient and authentication token) is managed via React Context. UI consistency is maintained using a custom CSS module system.
  • Backend API: Built with FastAPI to leverage native asynchronous request handling. The /compare-scans endpoint accepts image hashes, invokes the PyTorch inference script, and returns JSON containing bounding box coordinates and regression metrics.
  • Computer Vision Model: The core detection engine utilizes a robust YOLO architecture trained entirely on a carefully curated, manually labelled dataset of MRI scans. It processes images via OpenCV before passing tensors to the model.
  • Mock Database: To keep the demonstration lightweight and portable without needing a PostgreSQL cluster, patient data and scan histories are mocked securely within the application layer.

Technical Trade-offs

  • FastAPI over Flask: Python was mandatory due to the PyTorch dependency. FastAPI was chosen over standard Flask for its exceptional asynchronous performance and automatic OpenAPI schema generation, which drastically sped up frontend integration.
  • Local Inference vs. Cloud API: Model weights (approx. 150MB) are loaded directly into the FastAPI server RAM upon startup rather than relying on a paid external API. Trade-off: higher server memory utilization, but zero latency/cost for image transmission.

Infrastructure & Environment
