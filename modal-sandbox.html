Allium: Volunteer Platform

Project Definition

Allium is a volunteer organization management platform built for the COMP SCI 2207/7207 Web & Database Computing course at the University of Adelaide. It bridges the gap between volunteers and organizations through a centralized digital ecosystem for discovering opportunities, managing events, and coordinating community engagement.

My Role & Contributions

As part of a team within UG Group 12, I contributed to both the frontend static page development (Milestone 1) and the full-stack web application (Milestone 2). My work spanned database schema design, Express.js route architecture, session-based authentication, and the integration of Google OAuth for streamlined sign-in.

Key Features

  • Role-Based Access Control: Four-tier permission system (Guest, User, Manager, Admin) restricting actions based on authenticated session levels.
  • Organization & Event Management: Full CRUD operations for organizations, events, and updates with support for public and member-only visibility.
  • Google OAuth Integration: Single sign-on via Google using the google-auth-library, with differing profile edit capabilities for Google vs. local users.
  • NodeMailer Notifications: Automated email dispatch to subscribers when a manager creates a new event or update within their organization.
  • Event Attendance Tracking: Members can indicate attendance on events, and managers can view attendee lists for planning purposes.

User Stories

As a Guest, I want to browse organizations and public events, so that I can discover volunteer opportunities before signing up.
As a Registered User, I want to join organizations and RSVP to events, so that I can track my volunteer involvement and receive notifications.
As a Manager, I want to create events and post updates for my organization, so that I can coordinate activities and communicate with members.
As an Admin, I want to manage all users, organizations, and role assignments, so that I can maintain platform integrity and quality.

System Design

  • Route Architecture: Five modular Express routers — index.js (public routes), users.js (member actions), managers.js (org management), admins.js (platform oversight), and organizations.js (org data retrieval).
  • Session-Based Auth: express-session with secure, HTTP-only cookies. Three middleware guards (checkUserSession, checkManagerSession, checkAdminSession) protecting routes based on permission level.
  • Database Schema: Seven relational tables — users, organizations, events, updates, plus three join tables (user_organization, user_event, manager_organization) enforcing referential integrity via Foreign Key constraints.
  • File Uploads: Multer middleware handles profile picture and organization image uploads, storing binary data as MEDIUMBLOB in MySQL.
  • Rate Limiting: express-slow-down throttles requests after 100 hits per 15-minute window, adding 200ms delays to mitigate abuse.

Technical Trade-offs

  • MySQL over NoSQL: The highly relational nature of Users ↔ Organizations ↔ Events required strict FK constraints and join-table integrity that document stores cannot enforce natively.
  • Server-Side Rendering over SPA: Static HTML served from Express with AJAX calls for dynamic data. Avoided React/Vue overhead for a CRUD-heavy app where server-rendered pages kept the architecture simpler.
  • BLOB Storage over File System: Profile images stored directly in MySQL as MEDIUMBLOB. Trade-off: simpler deployment (no CDN), but increased database size and query overhead for image retrieval.
  • Session Cookies over JWT: Used express-session for server-side state. Trade-off: requires session storage server-side, but provides immediate revocation and simpler CSRF protection.

Quality Assurance & Testing

  • ESLint: Configured .eslintrc.json enforcing consistent code style and catching common errors across all route files.
  • HTML Validation: .htmlvalidate.json rules applied to all static pages to ensure W3C compliance and accessibility standards.
  • Manual QA: Walkthroughs simulating Guest, User, Manager, and Admin workflows to verify RBAC enforcement and data integrity before each milestone submission.
  • Input Sanitization: Server-side validation using the validator library on all user inputs to prevent XSS and SQL injection vectors.

Infrastructure & Environment

  • Dev Environment: VS Code Dev Containers (.devcontainer.json) ensuring consistent Node.js + MySQL development environments across team members.
  • Database Setup: webapp_database.sql dump with schema creation, seed data for 5 organizations, 20 events, 20 updates, and 11 user accounts for testing.
  • Session Security: Secure HTTP-only cookies with production HTTPS enforcement, session secrets via environment variables.
  • Rate Limiting: express-slow-down protecting all routes against brute-force and automated abuse.
